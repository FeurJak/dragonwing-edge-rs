# FP16 (Half-Precision) Path

This document describes the FP16 data type and operation support added in
task 003.

## Why FP16

The QRB2210 is memory-bound for inference workloads. Probe results in task
002 confirmed:

- Total heap budget: ~870 MiB (shared with display).
- Peak LPDDR4X bandwidth: ~14.4 GB/s.
- Max storage buffer range: 128 MiB.

FP16 doubles the effective memory bandwidth (2 bytes vs 4 bytes per element)
on activations and weights. Whether it also doubles arithmetic throughput
depends on the hardware (see open questions below); the bandwidth gain alone
is reason enough to support it.

## Hardware support summary

| Path | Status | Note |
|------|--------|------|
| Vulkan storage (`VK_KHR_16bit_storage`) | ✓ present | Load/store FP16 from SSBOs without unpack shims |
| Vulkan arithmetic (`shaderFloat16` + `GL_EXT_shader_explicit_arithmetic_types_float16`) | ✓ present | `float16_t` works in shaders; whether Turnip keeps the math in FP16 ALUs is unverified |
| CPU storage (FP16 → `u16` round-trip) | ✓ via software | Pure-bits conversion, no hardware intrinsics |
| CPU arithmetic on `float16x8_t` | ✗ unavailable | Cortex-A53 is armv8-A *without* the `fphp`/`asimdhp` extensions. FP16 math on CPU **must** go through F32. |

## `F16` representation in `dragonwing-core`

The `F16` type is a transparent wrapper over `u16` holding the IEEE 754
binary16 bit pattern:

```rust
#[repr(transparent)]
pub struct F16(pub u16);

impl F16 {
    pub fn from_f32(v: f32) -> Self;  // round-to-nearest-even
    pub fn to_f32(self) -> f32;        // exact for all finite values
}
```

Two design choices worth recording:

1. **No `half` crate dependency.** The conversion is ~60 lines of pure-bits
   work and `dragonwing-core` keeps its zero-runtime-deps posture. The `half`
   crate would buy us API ergonomics we don't need (`F16` is mainly an
   on-the-wire format, not an arithmetic type).
2. **Software conversion, not NEON intrinsics.** The AArch64 `vcvt_f16_f32`
   intrinsic is behind unstable Rust feature `stdarch_neon_f16`. Even with
   the intrinsic available, the CPU has no FP16 arithmetic — every "FP16"
   compute path widens to F32 before the FMA. Software conversion is fast
   enough for our use case (loading weights, occasional element-wise
   conversion).

## `Dtype` enum

The byte-oriented `Backend` trait stays unchanged. Ops carry their `Dtype`
parameter explicitly (Option B from the task 003 plan):

```rust
pub enum Dtype { F32, F16 }

impl Dtype {
    pub const fn size_bytes(self) -> usize { /* 4 or 2 */ }
}
```

This was chosen over extending `BufferKind` (combinatorial explosion) or
parameterising `Backend::alloc` (same shape but bigger surface).

## Op accumulation policy

**Every FP16 op accumulates in F32.** Reasoning:

- A 256-deep GEMM's accumulator overflows FP16's ~6.5e4 max with even modest
  weight magnitudes (1.0 × 1.0 × 256 = 256, fine; 10.0 × 10.0 × 256 = 25.6k,
  fine; 50.0 × 50.0 × 256 = 640k, **overflow**). Real networks see these
  magnitudes in dense layers.
- FP16 mantissa is 10 bits; accumulator precision degrades catastrophically
  past K ≈ 256.

So `gemm_fp16` reads FP16 inputs, computes in F32, and stores FP16 output.
The same pattern applies to `conv2d_fp16_nhwc` (CPU only — the Vulkan FP16
conv is deferred to task 004).

## Parity tolerances for FP16

The harness uses these bands (carry over to new ops in task 004 unless
empirical data forces a widening):

| Op | Tolerance | Why |
|----|-----------|-----|
| `fill_fp16` | exact on representable values, ULP on round | `from_f32` rounds; result is deterministic |
| `axpy_fp16` | 1e-3 relative | One FMA per element, F32 intermediate, FP16 round on store |
| `relu_fp16` | exact | Comparison and pass-through, no arithmetic |
| `add_fp16` | 1e-3 relative | Same as axpy without the scalar |
| `gemm_fp16` | 5e-3 relative | K accumulations in F32, FP16 round on store; tolerance reflects FP16 mantissa |
| `conv2d_fp16` (CPU) | 5e-3 relative | Same accumulation model as GEMM |

The `gemm_fp16` and `conv2d_fp16` numbers are notably looser than their F32
counterparts (1e-3 and 1e-4 respectively). This is mantissa-limited, not a
correctness margin — tightening it would make tests flap with no real signal.

## Vulkan shader pattern

FP16 shaders need three extension lines and the explicit `float16_t` type:

```glsl
#version 450
#extension GL_EXT_shader_16bit_storage              : require
#extension GL_EXT_shader_explicit_arithmetic_types_float16 : require
#extension GL_EXT_control_flow_attributes           : enable

layout(set = 0, binding = 0, std430) buffer YBuf { float16_t y[]; };
layout(set = 0, binding = 1, std430) buffer XBuf { float16_t x[]; };
```

The pipeline must enable `shaderFloat16` and `storageBuffer16BitAccess` in
its `VkPhysicalDeviceFeatures2` chain; this is wired up in the Vulkan
backend's context creation.

### Does Turnip actually run the math in FP16 ALUs?

**Unverified.** The spec allows the implementation to implicitly widen FP16
arithmetic to FP32 — correctness is independent of this, but throughput is
not. To answer the question definitively, run `axpy_fp16` and `axpy_f32` at
the same problem size on the device and compare GFLOPS:

- If FP16 ≈ 2× faster → genuine FP16 math.
- If FP16 ≈ same as F32 → only memory bandwidth win (still useful).

This bench is on task 003's bench list but is deferred at the time of
writing.

## CPU FP16 — bandwidth win, not throughput win

Cortex-A53 supports `armv8-A` *without* the `+fp16` arithmetic extension:

- `/proc/cpuinfo` HWCAPs should **not** contain `fphp` or `asimdhp`.
- `float16x8_t` exists in the NEON header but only the storage variants
  (`vld1q_f16`, `vst1q_f16`) execute on this CPU; arithmetic intrinsics
  silently widen.

So the CPU FP16 path:
- Loads FP16 (vectorised storage on AArch64, scalar conversion elsewhere).
- Converts to F32 in registers.
- Performs the actual math in F32.
- Converts back to FP16 on store.

The result: half the L1/L2 footprint, half the LPDDR bandwidth, *the same*
arithmetic cost. For small tensors the conversion overhead dominates; for
large tensors the bandwidth win is worth the conversion.

## Limitations carried into task 004

- **No FP16 conv on Vulkan.** The CPU FP16 conv works; the Vulkan FP16 conv
  shader needs to be added and validated. This is a known omission, not a
  blocker — the micro-graph test runs in F32 end-to-end.
- **No FP16 pool / softmax / maxpool.** These ops are dtype-uniform in the
  current implementation. FP16 variants are easy to add but not on the
  critical path.
- **No mixed-precision graphs.** A model that wants FP16 conv with F32 norm
  layers needs explicit dtype conversion ops; we don't ship those yet.
